# Inject prior assistant response into classifier input for short affirmations

When the user sends a bare affirmation ("yes", "go ahead", "proceed"), the existing code in `route_model()` inherits the cached session tier or floors to standard — it does not call the classifier. The invariant in `docs/agents/model-routing.md` states: "Short direct user affirmations inherit the cached tier when available; without one they use the configured floor. They must not overwrite the tier cache."

**This ADR amends that invariant** for the no-cache case. The affirmation-handling code path is modified to call the classifier *only when no cached tier exists*. When a cached tier is available, the existing early-return path (inherit without calling the classifier) is preserved unchanged. When no cache exists, the affirmation code path calls the classifier with enriched input (see below) to establish a tier for this turn and subsequent tool turns. If prior-response enrichment is unavailable (no text blocks in the prior assistant message), the classifier falls back to the configured floor behavior, preserving the invariant's fallback branch.

We add a `prior_response_summary` field to the classifier JSON, injected only when `is_short_affirmation()` is true AND the classifier is about to fire (no cached tier available). The user-prompt classifier system prompt must be amended to accept and prioritize `prior_response_summary` when present: the preamble should read "When prior_response_summary is provided, judge complexity ONLY from the context in prior_response_summary. Otherwise, judge complexity ONLY from the user's intent in final_user_text." This override ensures that the enriched context is not silently discarded.

The summary is extracted from the last assistant message in `payload['messages']` by walking backward to find `role='assistant'`, then processing the message's `content` field:
- If `content` is a `str`: use it directly
- If `content` is a list: collect text from blocks where `type == 'text'` (skip `tool_use`, `thinking`, `tool_result`, `image`, and any other block types), then concatenate with `'\n'` separator to preserve block boundaries
- Head-cap the result to the first N chars where N is configured via `auto_model_routing_prior_response_summary_limit` (default 1000)

Head-capping preserves the substantive task description that appears at the start of an assistant response ("I'll implement X by…"), rather than the closing boilerplate and code that accumulates at the tail. If no text is found (e.g., plain-string content is empty, or the prior message contained only tool-use blocks), `prior_response_summary` is not injected, and the classifier receives just the affirmation text. The classifier then sees what the user is agreeing to (if available) and can classify the combined intent accurately.

The classifier result on the affirmation path DOES write to the tier cache **when classification succeeds**. Because this code path fires only when no cached tier exists, there is no established tier to overwrite — the successful result creates the first cache entry for this context key. The cache key must be the composite context key mandated by model-routing.md: `(session ID, stable first-user-message hash)`, NOT the bare session key. This ensures subsequent tool-call turns within the same session read from the same cache entry, allowing them to inherit the established tier without re-classifying, which is both correct (they are executing the confirmed plan) and cheaper (no additional classifier calls). See model-routing.md for context-key composition rules. **If the classifier call fails** (network error, invalid response), the floor tier is used for this affirmation turn only; the tier cache remains empty, so the next non-affirmation turn in the session will attempt classification normally and potentially establish a tier. This preserves retry paths and prevents a transient classifier error from permanently routing a session at the floor. The "zero overhead" claim in the considered options above is corrected: the affirmation path with no cached tier adds one classifier network round-trip, not zero; all other turns (cached or non-affirmation) incur no additional latency.

**Interaction with ADR 0010 (weighted combination):** the weighted system-prompt + user-prompt blend (ADR 0010) applies to all classifier calls, including affirmation turns. When `is_short_affirmation()` fires without a cached tier and the classifier is invoked with `prior_response_summary`, the resulting user-prompt score feeds into the same weighted formula. Order of operations: (1) check for cached tier; if found, inherit and exit (model-routing.md invariant preserved); (1a) obtain `system_prompt_score` by consulting the LRU cache (check miss → dispatch isolated classifier → cache success only, fallback to 1.0 on failure); (2) inject prior response if available, (3) classify user prompt → user_score, (4) blend system_prompt_score and user_score using configured weights, (5) threshold → final tier. The final blended tier (output of step 5, after threshold comparison) is written to the tier cache to serve subsequent tool turns in the same session — not an intermediate score. Step 1a may execute in parallel with step 2–3 since there is no data dependency (system_prompt_score does not depend on user_score or prior_response_summary), allowing implementers to dispatch both classifiers concurrently via the isolated classifier call path.

## Considered Options

**Inherit cached tier only (status quo):** Correct when a relevant tier is cached, wrong otherwise. Doesn't handle sessions where the affirmation kicks off work that differs from prior complexity.

**Read last response from DB (`response_text`):** More reliable across client implementations, but adds a DB read per affirmation turn. Rejected in favour of reading from `payload['messages']`, which is always in-process. DB fallback can be added later if needed.

**Classify with just the affirmation text:** Routes to trivial/haiku every time. Poisons the tier cache for follow-on tool turns. Rejected.

## Consequences

- `RoutingSummary` gains a new optional field `prior_response_summary: str | None`.
- `to_classifier_json()` includes `prior_response_summary` when present.
- New config: `auto_model_routing_prior_response_summary_limit` (int, default 1000).
- The affirmation code path in `route_model()` is restructured: check for cached tier first; if found, inherit and return early (preserving the model-routing.md invariant). Only when no cache exists, call the classifier with enriched input.
- Text extraction from the last assistant message handles two content forms: if `content` is a `str`, use it directly (head-cap to limit); if `content` is a `list`, iterate over elements, check `isinstance(element, dict)` first to defend against non-dict items (bare strings, ints, None), and collect only `text`-type blocks via `element.get('text', '')` (skipping `tool_use`, `thinking`, `tool_result`, `image`, and any other block types). This defensive approach treats malformed or unexpected list elements as contributing empty strings, avoiding AttributeError. If no text is found in either form, `prior_response_summary` is not injected, and the classifier receives just the affirmation text.
- Latency and concurrency: affirmation turns with a cached tier incur no additional latency (early return). Affirmation turns with no cached tier and a cached system-prompt classification add one user-prompt classifier round-trip. When both caches are cold (novel system prompt + no session tier), two classifier round-trips are required: system-prompt classification (step 1a) and user-prompt classification (step 3). Implementations MAY dispatch these concurrently (max of the two latencies) or sequentially (sum of the two latencies) — both are conformant, subject to the isolated classifier call path constraints. All other turn types (non-affirmation) incur no additional latency. Concurrent affirmation misses are bounded by the number of simultaneous requests; the last successful write to the cache wins.
- **Validation:** startup config validation must assert `auto_model_routing_prior_response_summary_limit >= 1`; raise a `ConfigurationError` with readable text if the value is 0 or negative. A limit of 0 head-caps every prior-response summary to empty string, silently disabling enrichment on all affirmation turns with no warning.
- Requires `payload['messages']` to contain the full conversation history. Claude Code always sends it; other clients may not — the field is `None` and the classifier receives just the affirmation text.
- **Edge case — session-opening affirmation (no prior assistant message):** when a session opens with an immediate affirmation (e.g., user sends "yes" as first turn) or when the backward walk finds no assistant-role message, `prior_response_summary` is not injected. In this case, the classifier is dispatched with just the affirmation text (e.g., "yes") as input. The classifier will return a tier (typically trivial for a bare "yes"), and that tier IS written to the tier cache. Subsequent tool-call turns in the session inherit this tier. This is the correct behavior: the session's initial affirmation establishes a routing tier in the absence of prior context, and the tier cache ensures consistent downstream routing until a non-affirmation turn re-classifies. The implementation does not choose between alternative behaviors here — the classifier result is always cached to ensure deterministic session routing.
- **Updated model-routing.md invariant:** "Short direct user affirmations inherit the cached tier when available; without one, call the classifier — with prior-response context if available, otherwise with the bare affirmation text — and write the result to the tier cache to serve subsequent turns. Fall back to the configured floor only when the classifier call itself fails." **Implementation scope includes propagating this revised invariant to `docs/agents/model-routing.md`.**
