# Combine system-prompt and user-prompt tier scores with configurable weights

Routing accuracy suffers when the user's message is short or ambiguous but the agent role (encoded in the system prompt) clearly implies a complexity band. Conversely, a "file search specialist" agent sending a complex-sounding prompt may not actually need opus. The system prompt is structural context about what kind of work the session does; ignoring it loses a stable signal.

Note: the "researcher sends 'go ahead'" case is handled jointly with ADR 0013. When `is_short_affirmation()` fires AND no cached tier exists (per ADR 0013 step 1), the classifier sees the prior assistant response as context (not the bare "go ahead" text); the resulting `user_score` reflects the complexity of the work being confirmed, not the affirmation. When a cached tier exists, the early-return path in ADR 0013 applies (step 1) and no classifier is called. The weighted combination then applies to that context-enriched score when classification proceeds. The two mechanisms compose: ADR 0013 enriches the user-prompt input and controls the cache-hit path; this ADR blends the classifier result with the system-prompt score.

We classify the system prompt separately — using a specialized classifier prompt keyed by `system_prompt_sha256` (computed inside `build_routing_summary()` in `model_router.py` from `payload['system']` when present, using the same serialization already used in `handlers.py:1568-1579`: `hashlib.sha256(json.dumps(system, sort_keys=True, ensure_ascii=False).encode()).hexdigest()`, and included in the returned `RoutingSummary` so `route_model()` can pass it to the LRU cache lookup without re-computation) — and blend its tier score with the user-prompt tier score using configurable weights:

```
weighted_score = (sys_weight × sys_score) + (user_weight × user_score)
```

Tier scores: `trivial=0`, `standard=1`, `deep=2`. The `weighted_score` is compared against two configurable thresholds (`auto_model_routing_trivial_threshold`, `auto_model_routing_standard_threshold`; defaults `0.75` and `1.50`) to select the final tier using this comparison: **trivial if `weighted_score < trivial_threshold`; standard if `trivial_threshold <= weighted_score < standard_threshold`; deep if `weighted_score >= standard_threshold`.** Weights are configured via `auto_model_routing_system_prompt_weight` and `auto_model_routing_user_prompt_weight` (defaults `0.30` / `0.70`); both must sum to `1.0`.

## Considered Options

**Floor only (system prompt sets a minimum tier):** Simpler and requires far less machinery (eliminates LRU cache + threading lock, two weight params, two threshold params, weighted arithmetic, and extra DB columns), but asymmetric — a high-complexity system prompt can only raise the tier, never moderate an over-classified user prompt. Example: with defaults `trivial=0`, `standard=1`, `deep=2`, thresholds `0.75/1.50`, a deep user-prompt (score 2) paired with a trivial system prompt (score 0) would yield tier = max(deep, trivial) = deep under floor-only logic, forever routing to opus despite a trivial agent role. With the blend (0.30 weight on system, 0.70 on user), the same case yields 0.30×0 + 0.70×2 = 1.40, landing at standard — correct for a trivial specialist, moderate cost. Floor only is rejected in favour of a true blend, accepting the added complexity for correctness on moderation cases.

**Equal weights (0.5/0.5):** Gives the system prompt too much influence; a "deep"-role agent asking "fix this typo" should still land on haiku, not standard.

**Hardcoded thresholds:** Rejected. Different deployments have different cost/quality trade-offs; thresholds should be tunable without a code change.

## Consequences

- Five new columns on `requests`: `system_prompt_tier`, `system_prompt_score`, `user_prompt_score`, `routing_weighted_score`, `system_prompt_classification_failed` (schema migration required).
- System prompt classification result is ephemeral (in-memory cache by SHA256); lost on restart. The cache is bounded by an LRU eviction policy: `auto_model_routing_system_prompt_cache_size` (default 256 entries) caps the cache; when exceeded, the oldest entry is evicted. This prevents unbounded memory growth in high-cardinality deployments (e.g., per-user injected system prompts).
- Concurrent cache misses for the same SHA256 each trigger an independent classifier call; the last write to the LRU cache wins. Redundant calls on cold-cache startup are bounded by the number of concurrent requests and are cheaper than introducing a new locking primitive into the routing module, whose concurrency rules are tightly specified.
- If system prompt classification fails (network error, invalid response), the weight falls back to `standard` (score 1.0) in-memory for this request only — fail-open to avoid penalising sessions whose system prompt the classifier can't reach. **Critically, failed classifications MUST NOT populate the LRU cache.** Only successful classification results are cached. This prevents transient errors from permanently blocking future retries for a given system prompt SHA256; a future request with the same system prompt will attempt classification again, not inherit the temporary failure.
- **When no system prompt is present:** `sys_score` defaults to `1.0` (standard), and the weighted formula applies normally. This treats "no system prompt" the same as "system prompt classified as standard" for routing purposes. All five columns are recorded (not NULL); `system_prompt_tier='standard'` and `system_prompt_classification_failed=0` when absent (per ADR 0011).
- System-prompt classifier calls must respect the classifier-isolation invariant (model-routing.md): they bypass provider kill-switch logic, are excluded from user-visible statistics and cost accounting, and no registry or selector lock may be held across them. The classifier must be invoked via a dedicated, isolated code path that does not flow through normal backend dispatch.
- The existing `classification` column retains the raw user-prompt label for backward compatibility; `routing_weighted_score` explains the final tier decision.
- **Latency impact:** system prompt classification adds a network round-trip on sessions with novel (uncached) system prompts. Requests with cached system prompts or user-only routing incur no additional latency.
- **Validation:** startup config validation must assert all of: (a) `abs(auto_model_routing_system_prompt_weight + auto_model_routing_user_prompt_weight - 1.0) < 1e-9` (sum = 1.0), (b) each weight is strictly `> 0` (positive; zero weights are not permitted as they cause wasteful classifier calls with no routing impact), (c) `auto_model_routing_trivial_threshold < auto_model_routing_standard_threshold` (thresholds ordered, ensuring standard tier has a non-empty valid range), AND (d) `auto_model_routing_system_prompt_cache_size >= 1` (cache must hold at least one entry; a value of 0 empties on every insert, forcing classifier round-trip on every request). Raise a `ConfigurationError` with readable text for any failure. Do not defer validation to first routing call.
- **LRU cache implementation:** the SHA256 → tier score cache must be thread-safe. Implement using `collections.OrderedDict` with a `threading.Lock` that is held only for short dict operations (get, setitem, move-to-end, popitem) — never across the classifier network call. This satisfies the concurrency invariant in `docs/agents/concurrency.md`: no lock held across network I/O.
- `RoutingSummary` gains a new optional field `system_prompt_sha256: str | None` (computed from `payload['system']` in the handler's routing summary build, before `route_model()` is called). This field does not expose prompt content — only a stable hash key for cache lookup and audit queries.
- **DB write pipeline for new columns:** the five columns (`system_prompt_tier`, `system_prompt_score`, `user_prompt_score`, `routing_weighted_score`, and `system_prompt_classification_failed`) must flow through three extension points (see ADR 0011 for the fifth column's semantics):
  1. `ModelRoutingDecision` gains five new optional fields: `system_prompt_tier: str | None = None`, `system_prompt_score: float | None = None`, `user_prompt_score: float | None = None`, `routing_weighted_score: float | None = None`, `system_prompt_classification_failed: bool = False`. These are populated in `route_model()` after the weighted blend is computed: set `system_prompt_classification_failed = True` only when classification was attempted and failed (network error, invalid response); set it `False` for success, no-system-prompt, and disabled-routing cases.
  2. `_extract_prompt_capture()` in `handlers.py` is extended to read all five fields from its `routing` parameter (following the ADR 0009 pattern) and include them in the returned capture dict.
  3. `record_request()` in `db.py` gains five new optional kwargs (`system_prompt_tier`, `system_prompt_score`, `user_prompt_score`, `routing_weighted_score`, `system_prompt_classification_failed`) that default to `None`/`False` and are passed to the INSERT. All existing call sites continue to work without modification (kwargs are optional). The one call site that passes prompt-capture data must be updated to pass all five fields.
